## 2. How derivatives were verified

Four verification layers. Knowing what each one **proves** (and does not) is the
whole point — a passing test is only as strong as what it actually checks.

### Layer 1 — Complex-step (CS): the reference truth
Perturb an input by `i·h`, read the derivative off `Im(output)/h`. No subtractive
cancellation, so it is accurate to machine precision and **step-independent**.
- Commit evidence: *"complex derivatives matching between 1e-40 and 1e-200"* —
  identical derivative across ~160 orders of magnitude of step size, the
  signature of a correct CS linearization.
- Proves: the differentiated **model** is primal-correct.
- Caveat: CS requires the function to be **analytic** (Cauchy–Riemann), which is
  stronger than differentiable. Nonsmooth ops (`abs`, `max`, comparisons) must be
  re-implemented correctly for complex arguments.

### Layer 2 — Forward AD vs Finite Difference (`test_jacVecProdFWD.py`)
Tapenade tangent routines (`_d`) vs an FD directional derivative.
- Proves: forward mode ≈ truth, **but** FD is noisy, so this is the weakest check.
- This is where SST is visibly struggling (see §5).

### Layer 3 — Dot-product / transpose consistency (`assert_dot_products_allclose`)
Enforces the identity **⟨J·u, v⟩ = ⟨u, Jᵀ·v⟩** — reverse mode must be the exact
transpose of forward mode.
- Both sides come from AD (no FD noise) → passes to near machine precision.
- Proves: reverse mode is the true transpose of forward mode.
- **Does NOT prove correctness against truth** (see §6).

### Layer 4 — NEW: reverse-fast dot-product test (added in this branch)
Same transpose identity applied to the "fast" state-Jacobian routines used to
build dR/dw for the adjoint preconditioner:

```python
dwDot = CFDSolver.computeJacobianVectorProductFwd(wDot=wDot, residualDeriv=True)
wBar  = CFDSolver.computeJacobianVectorProductBwdFast(resBar=dwBar)
# assert sum(dwDot*dwBar) == sum(wDot*wBar)
```

**Chain of trust:** CS proves forward is correct → dot-product tests prove
reverse/reverse-fast are the transpose of forward → therefore reverse is also
correct. This chain only holds if Layer 2 (forward vs truth) is tight. For SST,
that link is weak.

## 4. What did NOT work cleanly

### The recurring villain: the k-correction coupling
From `computePressureSimple` (`src/utils/flowUtils.F90`):

```fortran
p(i,j,k) = p(i,j,k) + factK * w(i,j,k,irho) * w(i,j,k,itu1)   ! factK = 5/3 - gamma
```

`itu1` is the turbulent kinetic energy *k*.
- In **Spalart–Allmaras**, *k* is not transported → `getCorrectForK()` is false →
  this term vanishes → differentiation is clean.
- In **SST**, *k* is a real state variable → this term couples the turbulence
  field into pressure → fluxes → residuals → forces. **This is the core reason
  SST differentiation is harder than SA.**
- Commit evidence of struggle: *"backwards partials agree with backwardsFast
  partials (k-correction disabled)"*, *"need to disable k-correction"*.
- **Important nuance:** the k-correction term itself is a plain product →
  perfectly **smooth**. Its trouble was **not** nonlinearity/smoothness; it was
  bookkeeping (see below). Do not conflate the two.

### Classic AD-of-CFD bugs (engineering, not fundamental)
- **Primal aliasing.** *"make sure `computePressureSimple` does not overwrite real
  `p(...)` values."* Symptom: *"forward vec-prod would change the residuals"* —
  the derivative sweep was mutating the primal state, which it must never do.
- **Halo/BC garbage.** `computeEddyViscosity` had to be clamped to skip boundary
  halo cells (`"saveguard against using values on BC's where they might not be
  assigned"`), otherwise unassigned turbulence values polluted the derivative.
- **Symmetry-plane normals** needed a robustness patch to differentiate.
- **Tapenade output** required post-processing to remove generated "garbage."

### Inherent model kinks (fundamental — smoothness, not degree of nonlinearity)
SST contains non-differentiable switches that AD/CS handle only at the currently
active branch:
- Eddy viscosity: `nu_t = a1*k / max(a1*omega, Omega*F2)` → `max` is a kink.
- Production limiter: `min(Pk, 20*beta*·rho*k*omega)` → kink.
- Blending F1, F2 via `tanh(...^4)` → smooth, no problem.

### Solver-side approximation (legitimate, but keep it straight)
- **ANK approximate turbulence Jacobian** (`ANK_useApproxTurb` / `approxTurb`):
  *"Disable production term for lower order ANK solver."* Fine as a
  **preconditioner** approximation — but this operator is deliberately **not** the
  true Jacobian, and must not be confused with the adjoint Jacobian.

## 5. The tolerance evidence (read this before trusting green tests)

From `test_jacVecProdFWD.py`, SST vs the SA baseline:

| Check | SA tolerance | SST tolerance |
|---|---|---|
| residual deriv, state perturb (wDot) | `rtol = 8e-4` | `3.11 - 1` = **2.11** (211%) |
| residual deriv, mesh perturb (xVDot) | `atol = 5e-4` | `rtol = 4.1e1` = **41** (4100%) |
| forces, mesh perturb (xVDot) | `rtol = 5e-4` | `1.7e0` = **1.7** (170%) |
| functions, wDot | `rtol = 1e-5` | `2.7e-3` |
| functions, xVDot | `rtol = 5e-6` | `3.7e-2` |

An `rtol` of 41 means the test passes unless AD and FD differ by more than 41× —
that is a NaN-guard, not a validation.

Coverage gaps:
- SST **adjoint** regression validates **only `cl`** (`evalFuncs=["cl"]`). Drag
  and moment sensitivities — the ones that drive shape optimization — are
  unguarded.
- CS test **drops `span`** (`for dv in ["twist", "shape"]`), so span sensitivities
  are not regression-checked.

## 6. Critical assessment

**The load-bearing correctness check (Layer 3) proves consistency, not
correctness.** Forward and reverse are differentiated from the same source with
the same k-correction handling, so they can agree to machine precision *while both
being wrong in the same way*. Correctness against truth comes only from CS
(Layer 1) and FD (Layer 2) — and for SST, the FD comparison has been loosened to
the point of non-verification, while CS coverage is narrow.

Be fair about **why**, per axis:
- **Mesh-derivative case (`rtol=41`)** has a partial excuse: with
  `turbResScale=[1e3, 1e-8]` the raw omega-residual is ~1e8, wall-distance
  recomputation under mesh motion is noisy, and near-converged entries drive
  relative error to infinity. FD is a genuinely poor reference here. **But** the
  correct fix is a **norm-relative or near-zero-masked** metric (or CS on that
  path), not inflating a global `rtol` to 41. As written, the mesh-coordinate
  derivatives are effectively unverified.
- **State-derivative case (`rtol=2.11`)** has **no** such excuse. State-perturbation
  FD is far cleaner than mesh FD, so 211% relative tolerance is a real signal that
  the derivative through the k-coupling is not tight — not just FD noise.

### Recommended before trusting this for gradient-based optimization
1. Replace the two blown-out FD tolerances with a **norm-relative** metric and
   re-tighten.
2. **Root-cause the `rtol=2.11` state-derivative case** — it is the cleanest FD
   reference available and it is still off.
3. Extend **CS validation to `cd`, `cmz`, and `span`** before trusting gradients
   on anything but lift.
4. Separate the two failure piles explicitly in the code/tests: inherent kinks
   (max/min limiters → may need smoothing/regularization) vs engineering bugs
   (aliasing, halo assignment → fixable). The fix differs by pile.

## 7. Conceptual note — "linearized" does not mean linear physics

The derivative operator (Jacobian) is a **linear map at each point** — that is the
definition of a derivative, `f(x+h) = f(x) + J(x)·h + O(h²)` — not a linear
surrogate for the physics. AD/CS/adjoint compute the **exact** derivative (to
machine precision) of the fully nonlinear code as written. Nonlinearity only bites
via (a) **extrapolation** over finite `h` (an outer-solver concern: more Newton
iterations, line-search shrink — not a derivative-accuracy concern), and (b)
**non-smoothness** (kinks: `max`, `min`, `abs`, limiters, branches), which is the
real risk. The correct question is not *"is this code very nonlinear?"* but
*"is it differentiable at my operating point, and is the discrete residual I am
differentiating the same one I am converging?"*
